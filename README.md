# Turbopack chunk-group fan-out reproduction

A stock Next.js App Router app whose shape makes Turbopack's chunking fan out: 300 server-component routes (`app/r<i>/page.tsx`) each render a sliding window of 100 of 200 shared `"use client"` components (`components/shared<j>.tsx`), each of which lazily imports 3 of 600 leaf client components (`lazy/leaf<k>.tsx`, 30 hook lines each), and every leaf lazily imports 2 other leaves. 1,106 files, 11 MB of source, no third-party dependency beyond `next`, `react`, `react-dom`.

With nested async chunking (the default in `next build`) Turbopack computes one async chunk group per (dynamic import × parent chunk group), so a 1,106-file app becomes a 9–10 minute build whose filesystem cache is 7.4 GB.

Generated by a small Rust program (`tpgen`, source in `tools/tpgen.rs`); the parameters are at the top of that file.

```sh
pnpm install
# filesystem cache on (the default)
rm -rf .next && /usr/bin/time -v pnpm next build
# filesystem cache off
rm -rf .next && FS_CACHE=0 /usr/bin/time -v pnpm next build
```

## Measured (next 16.5.0-canary.8, Node 24.18.0, Linux x64, 166 cores / 223 GB, `/usr/bin/time -v`)

| build | wall | `Compiled successfully in` | persist | peak RSS | user CPU | `.next/cache` |
|---|---|---|---|---|---|---|
| cache on (default) | 635.1 s | 9.1 min | 43 s | 46.0 GB | 5,916 s | 7.4 GB (773 files) |
| cache off (`FS_CACHE=0`) | 609.8 s | 8.7 min | — | 32.0 GB | 4,370 s | — |

A second run on another box of the same class gave 637.0 / 617.0 s, 45.8 / 32.1 GB.

The same generator without nesting (500 routes × 300 shared × 1,000 leaves, 1,806 files) builds in 233.7 s cache-on / 221.2 s cache-off with a 2.7 GB cache: the second level of lazy-inside-lazy is what multiplies the chunk groups.

## What this does and does not reproduce

- Reproduces: the chunk-group fan-out and the resulting cache size (7.4 GB for 1,106 files, 65 % of it chunk-group results and their asset flattenings in a large real app), and the cache's extra cost in CPU (+35 %) and memory (+44 %).
- Does not reproduce: the 2.1–2.6× wall-time slowdown of the cache-on build seen on a large private application (613 endpoints, ~131k module instances, 262k async chunk groups). That slowdown is a single-threaded `AggregationUpdateQueue` phase that needs the real app's fan-in (tens of thousands of references per chunk group, each with thousands of uppers); see the issue this repository is linked from.
